## Confirmed intent and scope

Find which protocol, DNS mode, ports, and packet priority settings give the best connection to one owned server for FPS online games. A separate future project will use the findings to build a gaming proxy intended as an ExitLag alternative.

| Area | Confirmed requirement |
| --- | --- |
| Platforms | Windows 11 client only; Linux server only; 64-bit ARM64 and x86-64 on both; broad mainstream Linux coverage including CentOS, Ubuntu, Fedora, Arch, and other major distributions; exact version limits pending (T12) |
| Server count | One owned measurement server per comparison |
| Traffic | Real TCP, UDP, TLS, QUIC, WireGuard, Hysteria2, and DNS experiments |
| Protocol setup | The tool manages its own protocol endpoints, credentials, sessions, and cleanup |
| Protocol extensibility | Add new probe protocols in later releases through a common adapter contract, without broadly rewriting the measurement engine, dashboard, configuration, or reporting |
| DNS | Explore port controls, direct valid DNS, and resolver-mediated data tunnels, including DNS transport variants |
| Ports | Configurable destination/listening ports, optional fixed client source ports, selected-port comparisons |
| QoS | Independent packet priority markings for client-to-server and server-to-client traffic |
| Workload | Small, frequent, sustained, bidirectional FPS-like traffic |
| Result | Evidence-based comparison of timely delivery, latency tails, jitter, loss/late data, spikes, and stalls |

This repository does not implement a gaming proxy, capture/forward real games' traffic, select relay routes, switch routes automatically, or provide multipath/session migration. Traffic shaping, bandwidth control, and queue management belong to the future proxy. Scheduling configurable test traffic and validating under externally generated load are measurement functions, not shaping features.

The intended workflow does not require separately installed and manually configured WireGuard/Hysteria2 services. Supported libraries or managed bundled components may be used; the tool owns their lifecycle. Self-contained handling does not promise privilege-free operation or eliminate external inputs: real operation needs access to the server, suitable port/network permissions, and, for recursive DNS experiments, a domain/zone delegated to the measurement server and selected resolvers. The tool cannot control independent resolver policy.

## DNS experiments

| Case | What to compare |
| --- | --- |
| Ordinary-port UDP | Direct non-DNS baseline to the owned server |
| Raw UDP on port 53 | Same workload/server to investigate port-related treatment; label as non-DNS |
| Direct DNS over UDP | Valid data-bearing queries/replies on port 53 and selected alternatives |
| Direct DNS over TCP | Valid framed DNS exchange; distinguish stream behavior and setup |
| Direct encrypted DNS | DoT, DoH, and DoQ; identify actual transport/version and authenticate the endpoint |
| Resolver-mediated DNS tunnel | Query unique names in the delegated zone through a chosen recursive resolver; correlate receipt/replies at the owned authoritative server |
| Resolver-access transports | Supported UDP, TCP, DoT, DoH, and DoQ access; keep unavailable capabilities explicit |
| Downlink strategies | Independently ready server data retrieved by client queries; include queue residence, polling cadence, empty polls, batching, and backlog |

Preferential DNS treatment by the ISP is a hypothesis. The ISP might classify by port, packet contents, destination, or combinations; an RTT difference alone does not establish which mechanism it uses. The recursive resolver introduces hops but is not another owned measurement relay. Its onward transport, source port, and markings are outside the tool's control.

Validate unique run/message identities and intended server receipt. Ordinary lookup latency, cached answers, redirected traffic, and unrelated DNS services do not prove end-to-end data-tunnel performance. Exercise caching/TTL, repeated queries, interception, truncation, fallback, encoding expansion, query/record size limits, fragmentation/reassembly, rate limits, and timeouts. Record actual fallback/retry costs and transport changes. Do not assume the resolver's authoritative hop uses the client's access transport.

Report usable payload and wire overhead. Test sustained bidirectional traffic, not isolated queries alone. Server-originated data must become ready independently of client queries so measurements expose polling delay. Calibrated timing or a valid local observation method is necessary before calling this true cross-host one-way latency.

## Port selection

Configure server/destination ports per profile and optionally bind a client source port where supported. Record requested and effective local bindings and remotely observed endpoints when available. NAT may rewrite source ports; local binding success does not establish the public value. Recursive DNS access-port selection does not control the resolver's onward authoritative port.

Coordinate listeners sharing address/transport/port through sequential trials or verified multiplexing. Occupied/privileged ports, unsupported bindings, fixed-source collisions, and blocked traffic produce explicit outcomes. Do not silently substitute ports or take over existing listeners. Baseline and default ports are not finalized.

## Independent packet priority

The proposed control is DSCP, with named presets and explicit numeric values in IPv4 DS/TOS and IPv6 Traffic Class. Preserve the separate ECN bits and the transport's congestion behavior; ECN is not an arbitrary priority knob.

Set each direction independently. Compare unmarked traffic, upstream-only marking, downstream-only marking, equal markings in both directions, and asymmetric combinations. Changing the client's socket does not configure server-originated packets.

For tunneled/encapsulated modes, apply the setting to the actual outer IP traffic visible to routers; keep inner markings separate. Managed integrations must expose this capability or report the limitation. Applying only an inner marking is not a successful outer-marking test.

| Evidence | Meaning |
| --- | --- |
| Requested | Profile's selected value, independently for each direction |
| Applied | OS/component accepted, rejected, unsupported, or unknown; API success alone is not wire proof |
| Observed at sender | Actual emitted marking where capture/telemetry permits; otherwise unknown |
| Observed at receiver | Arriving marking where supported; otherwise unknown; identify the observed DNS hop |
| Measured effect | Repeated matched comparison of actual delivery quality |

Preservation does not prove routers granted priority; rewriting does not reveal where it occurred. Neither endpoint controls ISP queues or independent recursive-resolver outbound markings. Do not silently apply global network/QoS policies to make a test work.

The first-slice contract selects calibration exchanges/model/failure gates; cadence/error/expiry values are explicit validated inputs with evidence provenance.

## Timing and scheduling correctness

- Use host-local monotonic clocks for durations and wall time for labels. Different hosts' monotonic timestamps cannot be subtracted.
- Record application RTT from local send/receive boundaries. Record server receive-to-send processing duration separately; report processing-corrected RTT only when both intervals are valid. Preserve both values and flag impossible or missing timing rather than clamping it.
- Corrected RTT is not pure network delay: scheduling, socket/transport queues, and tunnel processing may remain. State timing boundaries and precision; keep submission and scheduling delays visible.
- Directional one-way delay support and clock calibration are required under F09; usable measurements depend on validated calibration, drift tracking, and uncertainty. Unqualified one-way numbers are unavailable when that evidence is insufficient. RTT/2 is only a symmetry-based estimate.
- Schedule sends independently of replies. Record planned/actual sends, blocked/skipped submissions, queue growth, and local failures. A stalled stream must not lower the reported offered rate invisibly; bound outstanding work and queues.
- Configure payload size, bidirectional/asymmetric rates, run length, warmup, deadline, and final observation grace period. No universal FPS values are selected.
- Separate setup, cold/resumed handshakes, established-session delivery, reconnect, and optional idle/resume phases. Test immediate RTT exchanges and independently generated downstream data.
- State the origin of deadlines. Local RTT deadlines can start at scheduled send time; cross-host directional deadlines need calibrated clocks or a defined valid observation method. Otherwise report directional counts/gaps/order without invented one-way timeliness.

## Delivery accounting and statistics

Use run/session/message identities and reconcile sender/receiver evidence in both directions. Distinguish planned sends, attempts, accepted submissions, local failures, skipped sends, unique arrivals, duplicates, reordering, late arrivals, missing messages, stalls, disconnects, and reconnects. Keep original observations when a later arrival changes classification.

State denominators and collection windows. An accepted submission is not proof of on-wire transmission; local scheduling failure is not network loss. Reconciled unique counts support loss estimates for unreliable delivery. Complete stream delivery does not prove zero underlying packet loss; report late delivery and stalls, and identify supplemental retransmission counters by source.

Stop new sends, then collect delayed traffic/final server evidence for the documented grace period. Keep late records outside the main window. Canceled runs, missing remote evidence, or unfinished observations are incomplete/unknown, not fabricated clean loss rates.

Report min/max, median, p95/p99, sample counts, and any additional justified metrics with percentile method and rounding. Completed-response percentiles must appear beside timeout/deadline outcomes so missing slow traffic stays visible. Small samples do not justify precise tails.

Define jitter and ordering explicitly: RTT variation and receiver inter-arrival variation are different observations. Define spike baseline, threshold, grouping, duration, peak, and associated failures. Proposed additional burst-pattern metrics remain in the suggestions backlog.

Use Go standard networking for raw UDP and framed TCP, `golang.org/x/crypto/ssh` for the embedded authenticated control endpoint, and the YAML organization's `go.yaml.in/yaml/v4` parser for profiles. Use standard JSON/CSV, random generation, SHA-256 and HMAC packages; platform socket/QoS support stays behind its own boundary. Exact compatible releases, licenses and transitive requirements are checked/pinned before the first authorized build. No benchmark tools are embedded or bundled. The maintainer [YAML repository](https://github.com/yaml/go-yaml) directs new projects to v4; Go's [SSH API](https://pkg.go.dev/golang.org/x/crypto/ssh) exposes server/client and custom channels. These are component selections, not build evidence.

| Contract operation / description | Responsibility |
| --- | --- |
| Describe | Stable adapter ID and contract version; validated typed option descriptions; supported platforms/address families, directions, payload limits, ports, trust, outer-marking and observation capabilities |
| Validate | Common profile validator plus adapter options/capabilities; reject unsupported required behavior before readiness, with structured reasons |
| Prepare / Ready | Own only created listeners/connections; return effective bindings, session identity and role-specific settings; complete authenticated data-path binding before ready |

#### Pairing, credentials and SSH coordination

Generate Ed25519 host and client identities locally at their respective endpoints. A public JSON pairing bundle carries `schema_version`, `server_id`, `control_address`, `control_port`, `host_public_key`, `host_key_fingerprint` and `supported_contract_versions`. Client public enrollment records carry `client_id`, `public_key`, `enabled` and optional explicit `expires_at`; absence of expiry means no automatic expiry, visible in the authorization view. Import/export is through an already trusted channel, not unauthenticated network enrollment. Only the server application's authorization store grants access. Support references to compatible existing SSH private keys without copying or changing the source file; incompatible types/formats fail explicitly.

Generated private-key files live in the selected application data directory with owner-only Linux permissions and a Windows ACL restricted to the owning user and required OS principals. Failure to establish restrictive access is an error. Optional encrypted existing keys require an in-memory passphrase prompt; no passphrase is saved or logged. Public pairing/profile/result files contain key references/fingerprints, never private keys, enrollment secrets or per-run MAC keys. Atomic explicit authorization-store updates preserve the previous valid store on failure. Disabling/removing a client or reaching an explicit expiry cancels its active run as partial. Replace host identity only by an explicit local operation followed by trusted client re-import; no silent trust-on-first-use or identity fallback. TLS certificate loading/renewal remains future TLS-carrier work.

The embedded endpoint accepts SSH public-key authentication against that store, verifies the server's imported host identity on the client, and permits application channels only. No shell/exec/SFTP/forwarding capability is part of this endpoint. A versioned control channel carries plan/readiness/start/stop/liveness messages; separate calibration and report-transfer channels share the same SSH connection. Their scheduling and bytes are recorded; multiplexing cannot remove underlying TCP head-of-line blocking. Application-owned startup needs no system SSH service or settings changes.

Control frames are a four-byte big-endian unsigned length followed by UTF-8 JSON, at most 1 MiB of JSON per frame. Envelope fields are `schema_version`, `type`, `request_id`, `run_id`, `session_id` and `body`; messages outside the valid lifecycle or with unsupported versions are rejected. Reports are transferred in bounded numbered chunks with checksums, acknowledged offsets and a final content hash, not a single oversized JSON frame. There is no automatic reconnect/resume in this slice.

Current control implementation: `sneaky-port/control/v1` supports hello/prepare/confirm/start/heartbeat/stop with unique request IDs and frozen identities. Heartbeats expose lifecycle status only. During a finite run, one `sneaky-port/calibration/v1` channel retains live clock captures; after stop, one `sneaky-port/report/v1` channel transfers server evidence. Premature/extra channels are rejected. Explicit IP pairing, strict JSON and initialized service/resource ceilings remain required. The sequence is authenticate, negotiate capabilities/versions, validate/freeze the normalized plan, prepare sockets, bind/authenticate the data path, acknowledge both roles' effective settings, start, warm up, measure, drain, reconcile and close. Each host records its own start anchor when it processes the start exchange; neither simultaneous starts nor equal phase clocks are claimed.

One active measured run per client and per server avoids unplanned contention/listener collisions. Control or heartbeat-lease failure stops new data at both endpoints when detected, drains no longer than the configured grace/stop budget, preserves each endpoint's report and releases owned resources. A server lease independently bounds cleanup if the client disappears. Missing server records leave remote delivery unknown; local reports are retained for later manual import/reconciliation. Liveness, setup, write and shutdown timeout values are explicit validated inputs, not hidden network-loss thresholds.

#### UDP/TCP payload and timing boundaries

The application message has a 92-byte big-endian header, configurable test-content bytes and a 32-byte HMAC-SHA-256 tag. Header layout, in order:

| Field | Bytes / interpretation |
| --- | --- |
| `magic`, `wire_version` | 4 ASCII bytes `SPV1`, then unsigned 16-bit version 1 |
| `kind`, `origin_direction` | 1 byte each; kinds bind-request=1, bind-ack=2, data=3, receipt=4; origin directions client=1, server=2 |
| `lifecycle_phase`, `flags`, `reserved` | 1, 1, 2 bytes; warmup=1/main=2 for data and echoed receipts, binding=0; flags/reserved zero in v1 |
| `run_id`, `session_id` | 16 bytes each |
| `phase_id`, `sequence`, `content_length` | Unsigned 32-, 64-, 32-bit values respectively; wire phase ID is the normalized phase index; binding uses zero phase/sequence outside the data ledger |
| `origin_epoch_id`, `peer_epoch_id` | Unsigned 32-bit IDs referring to host-local epochs in run records |
| `origin_attempt_ns`, `peer_arrival_ns`, `peer_receipt_attempt_ns` | Unsigned 64-bit host-local offsets; peer fields/epoch zero in data; receipt echoes origin time/epoch/identity and carries its receiver's arrival/receipt-attempt evidence |

Data carries the selected content pattern; receipts carry zero content bytes, retaining the data identity. Bind messages carry a 32-byte server-issued challenge as content, outside workload counts. Fixed message overhead is 124 bytes; a zero-content receipt is 124 bytes. UDP carries one whole message per datagram. TCP prefixes each whole message with a four-byte big-endian length, at most the agreed cap; prefix/metadata/tag/receipt overhead is separate from configured content. Invalid lengths are rejected before allocation; partial frames never become delivery samples.

The server generates fresh random session ID and separate 32-byte keys for each physical traffic direction after authenticated plan agreement, transferring keys only over SSH. HMAC input is ASCII `sneaky-port/probe/v1` followed by a zero byte, the 32-byte plan digest, a two-byte big-endian adapter-ID length plus UTF-8 adapter ID, then the complete header/content; verify using constant-time tag comparison. The physical sending direction chooses the key even for a reverse receipt. No measurement-payload encryption is added to raw UDP/TCP. HMAC is authentication, not TLS or a tunnel. Go's [HMAC documentation](https://pkg.go.dev/crypto/hmac) supplies the tag-verification primitive, not validation of this proposed wire protocol.

Before readiness, the client proves knowledge of its session key on the data connection using the challenge; the server acknowledges only valid bounded bind requests and locks the observed UDP peer/established TCP connection to that session. No UDP endpoint migration or raw-UDP retransmission in this finite slice. Wrong tuple/session/tag/version, impossible scheduled identity, tampered content or old-session replay is rejected and recorded within budgets. Valid active-session duplicates are counted separately, do not add RTT samples, and do not trigger repeated receipts or fresh downstream data. Downstream scheduled traffic starts only after authenticated binding and start agreement; responses to binding do not exceed request size.

For each datum/receipt, the writer takes the submission-attempt timestamp after queue waiting and immediately before encoding/authenticating/writing that frame. Record first socket-call and complete/partial-write timings separately; encoded `origin_attempt_ns` uses this declared application boundary. Arrival is captured when a complete datagram/frame has been read, before verification; only subsequently valid frames become eligible arrivals. Thus application one-way includes serialization/authentication/transport effects and is not an on-wire timestamp measurement. Receipt processing is receiver arrival to its receipt submission-attempt boundary; elapsed RTT is origin submission attempt to first valid receipt's captured arrival. Scheduled-origin completion also includes sender queue/scheduling delay. Invalid processing correction stays unavailable/flagged, never clamped into plausible delay.

#### Phase, scheduling and resource policy

Phase intervals are half-open on each host's monotonic timeline: include the phase start, exclude its end. A steady rate `n/d` schedules offsets `floor(k * d * 1e9 / n)` for integer k from zero while the unrounded rational offset is inside the phase. Validate strictly increasing realizable slot times and integer overflow. Repeating bursts use active/gap cycles from phase start, reset k within each active interval and schedule only offsets inside active/phase bounds; rate zero is represented as `quiet`. Quiet phases and burst gaps generate no planned data, while receipts remain eligible.

Warmup uses the first configured phase's directional settings, truncated/repeated for the explicit warmup duration, with separate identities; measurement restarts that phase pattern at its own main anchor. Each origin sequence increases across warmup and all phases without reuse. A datum, receipt and deadline remain attributed to their originating phase. A deadline override is resolved before freezing; omission inherits the explicitly configured run deadline. Completion at the deadline is on time; after it is late. Grace includes events strictly before its recorded end; events at/after cutoff remain out-of-window records and do not change finalized metrics without an explicit new analysis revision.

Independent scheduling accounts for every planned slot. Admit data only if data message/byte, outstanding and evidence budgets allow; otherwise record `skipped_local` with its reason and continue without catch-up. At a late scheduler wake, account all due slots, skip earlier overdue slots as `skipped_scheduler`, and admit at most the latest due slot if its lag is within explicit `max_schedule_lag_ns`; otherwise skip it too. A single slightly late slot within that allowance is still sent, with actual lag recorded. One bounded writer per physical direction uses FIFO admission with reserved receipt capacity, without interrupting a partially written frame. Receipt-capacity exhaustion is a local receipt failure, visible independently of data delivery. Complete an admitted frame within its configured write timeout or terminate the affected session as partial, preserving attempted/partial/unknown outcomes. Stream disconnects do not reconnect silently.

Queue accounting includes waiting and active work until the write callback returns. `queue_bytes` counts authenticated frames (124 plus data content), excluding TCP/outer framing. Data ceilings are `queue_messages - receipt_reserve` and `queue_bytes - 124 * receipt_reserve`; receipts share FIFO order and total caps. [Queue code](internal/writer/queue.go) timestamps/encodes through caller callbacks after waiting, retains partial bytes and terminates failed writers; profile feasibility stays conservative.

[Frozen windows](internal/worker/windows.go) and [shared workers](internal/worker/endpoint.go) now cover warmup/main/burst/quiet schedules, original identities and deadline expiry. Expiry releases outstanding admission strictly after deadlines, evaluated before new admissions, while retaining late-receipt identities. [Shared accounting](internal/engine/endpoint.go) connects events/tickets to the ledger and charges actual internal JSONL observation bytes against the run-wide `event_bytes` cap; these records are in memory, not the future persisted schema.

TCP uses the same workers/collector with complete-frame arrival timestamps and prefix-inclusive transport byte evidence; partial reads never add deliveries, and any failed/partial write terminates the segment. Local application receipt stalls never prove TCP network-packet loss. [Finite lifecycle](internal/engine/finite.go) now owns local anchors, physical-phase writer marking, grace and bounded cancellation. Marking evidence names the phase selected before encoding/write, independently of the original message identity; quiet phases update on the next outgoing frame and grace retains the final setting. API timing and a frame spanning a boundary do not establish exact on-wire transition timing. The server interrupts local I/O at its cutoff and retains the underlying connection until control stop/lease cleanup, preventing an earlier server cutoff from forcing early peer TCP EOF. Read errors observed at/after the finite cutoff stay outside-window evidence rather than truncating the completed window. Local file budgets/finalization are implemented in [task 12](ROADMAP.md#12-persist-bounded-local-raw-evidence-and-summaries-completed); local replay/export and authenticated remote reconciliation are implemented. [Queue evidence](WORK_LOG.md#2026-10-11-bounded-writer-queues), [UDP evidence](WORK_LOG.md#2026-10-11-udp-phase-accounting), [TCP evidence](WORK_LOG.md#2026-10-11-tcp-integration).

Cancel/control loss/resource-storage failure stops generation and fixes a truncated planned observation window; it does not manufacture planned slots after the stop point. Drain remains bounded by grace and shutdown budgets. Receipts arriving after the stop still refer to original identities; final missing/late counts use actual cutoffs and complete compatible ledgers. No complete-run percentages from an interrupted full-run schedule.

#### Calibration and one-way evidence policy

Use application-local monotonic clock mapping, never implicit system-clock changes. Maintain repeated authenticated four-timestamp exchanges on the SSH calibration channel: client request capture t1, server complete-request arrival t2, server response submission capture t3 and client complete-response arrival t4. Correlate calibration IDs/epoch IDs, preserve send-call/serialization costs and invalid samples, and record cadence, sample/window counts, age and expiry. Use a bounded recent window with at least two time-separated valid exchanges for a drift estimate; all retained valid constraints must be checked, not only a favorable minimum-RTT sample.

Task 15 implements capture. `samples` is the minimum recent valid count, `window` caps recent attempts including invalid ones; absolute cadence skips overdue slots without catch-up. t1/t3 precede response/request serialization, t2/t4 precede JSON decoding; a follow-up frame preserves server send-call costs without changing t4. Raw client `clock_capture` events retain both host epochs, correlated response identities, invalid/incomplete exchanges and exact application bytes. Recent snapshots identify their local `as_of_ns`, age and strict `age > expiry_ns` expiration. Frozen cadence demand reserves requests and 4 KiB per raw capture within event/file ceilings; storage admission is shared and nonblocking, with separate calibration file reserves. Missing/bad/stalled calibration does not invent one-way values or cancel working data/control. Channel cancellation is bounded; if SSH itself blocks close/write, shutdown closes the owned connection as control failure. The SSH API's one outstanding channel-open wait is released at connection teardown.

Task 16 implements post-reconciliation model revisions and directional results in [one_way.go](internal/control/one_way.go). Every capture freezes a recent-window revision, including invalid attempts/evictions; all valid unexpired constraints in that window must intersect. A result uses only the revision available at client send time upstream or client arrival downstream, with enough still-unexpired samples; later evidence cannot upgrade old messages. Both actual captures must fit the mapping lifetime under every feasible clock. Receiver/attempt identity and independent cutoffs reuse authenticated reconciliation gates. Missing remote captures are null; missing/inconsistent/foreign/expired clocks expose no value. JSON/JSONL/CSV replay reconstructs models from raw evidence, preserving hashes, IDs, age, signed intervals and explicit units. Delay is server-local nanoseconds upstream and client-local nanoseconds downstream, from pre-encoding attempt to complete application arrival, including local/carrier buffering. Derived model/result detail admission charges exact serialized bytes against min(event budget, 256 KiB); exact status and omitted-detail counts remain visible. No profile text or imported summary can enable independently verified bounds; production remains estimate/unavailable until task 28 supplies that evidence.

The model maps client offsets c to server offsets as `S(c) = a + b*c` within a declared validity interval, b positive. Nonnegative transit gives constraints `a + b*t1 <= t2` and `a + b*t4 >= t3`, widened for measured timestamp uncertainty and declared model error. These bound unknown directional asymmetry instead of asserting symmetry. Fit offset/drift within feasible constraints, report the full uncertainty envelope, and invalidate inconsistent/expired epochs or constraints. Rate-change uncertainty between exchanges must be supported by an explicit clock-quality/drift bound and source; an empirical straight-line fit alone is not such a guarantee. At b=1 with ideal captures, the interval reduces to `[t3-t4, t2-t1]`; its midpoint is only an estimate. This interval policy is our design inference, not an implementation of the NTP clock discipline. [RFC 5905 timestamp equations](https://www.rfc-editor.org/rfc/rfc5905.html#section-8) and [RFC 7679 uncertainty](https://www.rfc-editor.org/rfc/rfc7679.html#section-3.7) inform the review.

Propagate the feasible clock mapping and endpoint timestamp uncertainty to directional delay intervals at each data message's actual capture times. Record model/calibration/evidence IDs, lower/upper delay bounds, midpoint estimate, total uncertainty, age and assumptions. A wholly negative/impossible interval invalidates that derived result; retain signed raw evidence and crossing-zero intervals without silently clamping them.

- `calibrated`: clock/timestamp/model bounds are independently justified, captures are inside the validity window, total uncertainty meets the explicit `max_error_ns` policy, and fixtures have validated the method. Show intervals and uncertainty beside any point value.
- `estimate`: the model relies on unverified drift/asymmetry/timestamp assumptions or exceeds the allowed error; retain it visibly as an estimate, excluded from directional timeliness/winner claims.
- `unavailable`: missing, expired or inconsistent samples/epochs; no one-way value. Valid local RTT and delivery evidence remains usable.

Calibration failure alone does not stop an otherwise valid RTT/delivery run; its directional timing stays estimate/unavailable until evidence recovers. Retain model revisions rather than silently upgrading old samples. Wall-clock jumps cannot alter monotonic RTT; suspend/resume or unexplained monotonic-rate changes invalidate the mapping. Calibration sample/cadence/expiry/error/bound inputs are explicit profile/server policy, with their provenance; no default millisecond accuracy or oscillator tolerance is invented. Future runtime acceptance must exercise known offset, drift, asymmetric delay, SSH blockage, clock changes and expiry. A sampler producing estimates alone does not complete calibrated F09 support.

### Independent traffic and timing boundaries

Each endpoint schedules its own data messages at the configured rate, independent of received data or receipts. The receiver returns a correlated receipt for each valid data message; receipt traffic is additional overhead and cannot replace independently ready downstream data. Record receipt sizes/counts and adapter polling/retry traffic separately from offered application payload. A protocol unable to meet a requested workload reports that limitation rather than silently lowering it.

Confirmed on 2026-10-11 (T14): use independently scheduled data in both directions plus correlated application receipts, with information carried in the real protocol payload. The logical data payload contains measurement metadata and configurable test content; the receipt payload identifies the received message and carries the receiver-local processing interval when available. Proposed metadata concepts are version, run/session/workload-phase identity, origin direction, message kind, sequence, and content length; first-slice UDP/TCP names/encoding/widths are settled above; other-adapter mappings remain open. Carry these through the authentic adapter, including valid DNS encoding for DNS modes. Native transport acknowledgments alone do not establish receipt of a complete logical application message. Payload identities do not replace protocol-appropriate authentication.

Keep configured test-content bytes, encoded measurement-metadata bytes, total logical message bytes, receipt bytes, and outer transport overhead distinct. In the illustrative 128-byte workload, 128 bytes means test content, with metadata added separately; the dashboard must label that boundary clearly. Configurable content must not overwrite mandatory identities/framing. Sender-local timing records remain available for RTT recomputation; any transmitted timing values have an explicit host-local origin/units and cannot be subtracted across hosts without calibration. Do not put reusable credentials/private keys into measurement payloads or reports.

T14 explanation: client data message C1 goes to the server, which replies with a small receipt saying it received C1. The client measures elapsed time from sending C1 to receiving that receipt using its own clock. Separately, the server generates data message S1 according to its own workload schedule, and the client sends a receipt for S1. S1 is not merely the reply to C1. Both schedules continue while earlier receipts are outstanding. These application receipts are additional traffic, including over transports that already have their own acknowledgments. Missing data and missing receipts have different meanings: receiver records can show C1 arrived even if its receipt never returned. Receipt size, adapter mapping, and overhead limits remain open for integration review.

For each scheduled slot, record planned local time, submission attempt/completion, outcome, and queue/scheduling delay. Record receiver-local arrival and receipt submission times. Proposed elapsed RTT boundaries are original submission attempt to receipt arrival at the origin; also retain scheduled-slot-to-receipt duration for the scheduled-origin deadline. Submission acceptance time and duration remain separate evidence: an attempt or accepted write does not prove on-wire transmission. Receipts include the receiver's local arrival-to-receipt-submission interval for optional processing correction; invalid/missing correction stays explicit.

Use bounded outstanding work and queues; first-slice skip/admission behavior and required limit inputs are settled above under T14/T15. Scheduling continues to account for every planned slot under backpressure. No unbounded catch-up burst or hidden reduction of offered rate. Warmup and main-phase messages have distinct phase identities; a warmup response arriving in the main phase does not enter main-phase RTT statistics.

Without calibrated cross-host clocks, report directional send/arrival counts, receiver inter-arrival gaps, ordering, and local queue durations. Local receipt RTT is round-trip evidence from that direction's origin, not a one-way delay. A DNS downstream datum can become ready at the server before any poll; record server-local ready-to-dispatch queue residence and polling costs separately, without inventing ready-to-client one-way latency. The exact receipt mapping for every adapter remains an integration question.

### Accounting and summary concepts

Maintain separate data-delivery and receipt/RTT ledgers in each origin direction. Preserve events so later arrivals can revise classifications without erasing history.

| Ledger / concept | Required meaning |
| --- | --- |
| Planned slots | Every scheduled main-phase datum, including locally failed or skipped slots |
| Submission | Attempted, accepted, locally failed, skipped, or pending/unknown; retain partial-stream-write evidence and uncertainty |
| Data arrivals | Unique accepted identities seen at the receiver; duplicate arrivals separate; identify late/out-of-window arrivals |
| Reconciled missing data | Accepted identities absent from complete receiver evidence at the observation cutoff; report missing application data, not proven on-wire packet loss |
| Receipt completion | First valid receipt at the origin; duplicates do not add samples; receiver data receipt and origin receipt completion can differ |
| Deadline outcome | On-time, completed late, unresolved at cutoff, locally failed/skipped, or unknown; a late completion remains a deadline miss |
| Ordering | Within one origin/session/phase, first-arrival sequence below the highest previously seen is reordered; duplicates separate. This is application ordering, not underlying packet ordering. |
| RTT variation | Proposed absolute differences between adjacent completed RTT samples ordered by original sequence; report pair count and gaps/missing sequences. Distinct from receiver inter-arrival variation. |

Proposed scheduled-slot miss fraction: (late completions + unresolved receipts + locally failed/skipped slots) / planned slots, only when the origin ledger is complete through the declared cutoff. Show the components, plus accepted-submission miss fraction separately. Pending/uncertain writes stay explicit; do not force them into a definitive category. If a run is canceled or evidence is unfinished, report the known counts/window and an incomplete outcome rather than presenting the intended full-run fraction.

Proposed unreliable data-missing fraction: missing accepted identities / accepted submissions, only with complete compatible sender/receiver records and observation windows; show arrivals, duplicates, and cutoff alongside it. Unmatched identities or ambiguous writes require reconciliation warnings. Without remote evidence, missing directional delivery is unknown even when local RTT outcomes are available. Eventual reliable-stream delivery never becomes a zero network-packet-loss claim.

Keep elapsed RTT and scheduled-origin completion distributions separate, with on-time/late/unresolved counts adjacent. Proposed percentile method: nearest rank on sorted completed samples, rank ceil(p * n), with sample count and unrounded values retained for recomputation. Small samples and missing slow responses limit tail conclusions. First-slice spike baseline/threshold/grouping and receipt-stall rules are defined above; do not produce arbitrarily defined spike scores or imply S02 is adopted.
